# Central review backend contract (proposed)

The reviewed proposal is `docs/sql/central-review.sql`. The official CLI created `supabase/migrations/20260914174905_central_review_versioned_approval.sql` after the host permission update. The coordinating agent copies the frozen proposal there. This backend validation applied SQL exclusively in a disposable local database. It did not change production, dispatch notifications or run a transport. Complete the existing full-schema CI workflow before production deployment.

`central_review_source(_client_id uuid)` returns only `dossier_id`, `dossier_version`, `dossier_updated_at`, and a SHA-256 `scope_hash`. It requires a real authenticated staff user with access to the client. The dossier selection matches the application: current general `contexto` first, otherwise the latest current dossier. No dossier returns null dossier metadata; preparation refuses it. The scope hash covers the persisted client's commercial configuration, active project names/descriptions/scope/objectives/type/status/update dates and every current dossier's identity/version/content/summary/update date. Complementary dossier edits therefore invalidate the source even when the canonical context ID stays the same. Only the four neutral return fields belong in `reports.metrics.central_review_source`; hashed dossier contents never appear in that return value or client-readable metrics.

`central_review_prepare(_report_id uuid, _expected_version integer, _destination jsonb, _idempotency_key text)` requires an authenticated admin and nonempty summary/next_steps. Destination has exactly `channel` (`portal` or `whatsapp`) and a nonempty `recipient`; portal recipients must equal the report client UUID. It freezes `{report, destination, source, scope}`; `report` contains id, client_id, project_id, title, summary, next_steps, metrics, period_start, period_end, review_version. `scope` contains only plan_name and the service_keys whose configuration value is boolean true; arbitrary configuration objects are excluded. The return includes id, approval_id, client_id, report_id, payload_version, payload_hash, status, payload, created_at, decision_note and valid_until. A matching retry returns the same request; reusing a key with another report/version/destination fails. Requests expire after seven days. A new request invalidates unexecuted central requests in the same client, ritual and period (UTC report-created week fallback), preserving every record and other clients.

`central_review_decide(_approval_id uuid, _expected_client_id uuid, _expected_version integer, _expected_payload_hash text, _decision text, _comment text, _idempotency_key text)` verifies the authenticated admin, client, report version, snapshot hash, current source and expiry. Decisions are aprovado, rejeitado, alteracoes_pedidas or comentario. Rejection, adjustment and comment require text; comment records an audit event on the exact immutable snapshot, including approved or replaced versions, without reopening its decision. Current source, current report version, draft state and expiry checks apply to decisions; historical comments still require authenticated admin, matching client, snapshot version and hash. Approval also requires nonempty summary/next_steps. An exact decision retry returns the saved result; changed input with the same key fails. Reports are locked before approvals. The legacy decision RPC now locks its approval, enforces existing valid_until and refuses central rows, preserving the operator contract.

`operator_approvals.origin` preserves operator rows and permits central rows without a fictitious operator. Central snapshots are visible only to admins; legacy staff visibility remains. The existing payload trigger remains, and the additional central trigger also freezes destination and all snapshot identity fields. `reports.review_version` increments on content changes, invalidating only that report's unexecuted active central approvals; the existing published-report guard remains authoritative.

`central_review_events` is the audit/idempotency record and `central_review_dispatches` separates preparation/approval from delivery. This proposal implements no dispatch claim, sender, WhatsApp integration, external endpoint, sent/confirmed transition or automatic publication. An approved request is permission recorded, not evidence of delivery. Any future sender must atomically claim/revalidate current source and version before sending and handle uncertain delivery explicitly.

Validation: PostgreSQL 17.11, disposable database names restricted to `acq_isolated_central_*` on literal loopback. The complete proposal applied successfully. `central_review.test.sql` has 48 pgTAP assertions; `central_review_concurrency.test.sql` has 16 assertions using real dblink transactions. Covered calls include admin preparation/decision, replay/conflict, client CAS, historical comments, portal recipient binding, legacy denial/expiry, destination immutability, scoped staff source, admin-only snapshots/audit, content-version invalidation, preservation of the other tenant/history, stale canonical/complementary dossiers/project scope, missing summary/next step, existing published-report immutability, and zero invented dispatch. Concurrent scenarios cover duplicate prepare, conflicting decisions, report edit versus decision, same-period replacement and duplicate decision replay. The fixture copies actual role/scope helpers, reports RLS/column grants and the latest reports_secure_guard alongside the legacy approval table/trigger/function. Dossier content is TEXT, matching the actual schema. Storage ownership is an explicit fail-closed stub; these tests use null file_url and do not exercise storage.

Commands: `node scripts/test-isolated-db.mjs --self-test`, then `PSQL_PATH=<local psql> PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres node scripts/test-isolated-db.mjs` (set environment variables using the current shell). The runner includes Central and rejects non-loopback hosts or database names outside its generated isolated namespace. Logs go to `logs/database-isolated/`. The direct fresh-database run passed all 64 assertions; its log is in the task workspace's `work/central-review-validation-final.log`.

Compatibility evidence: the coordinator inspected the real canonical database read-only and confirmed the expected ledger head 20260912213638, report/approval columns, the single staff approval SELECT policy, TEXT dossier content, profile plan/service fields and project metadata types. It also confirmed the exact legacy function anchor used by the fail-closed patch, the app_private schema and existing reports_secure_guard. This is not a full schema replay: Docker is unavailable locally. `.github/workflows/supabase-db-tests.yml` performs the complete Supabase replay and these isolated contracts in CI. Remaining production triggers/defaults must pass that job. Source freshness is checked during the database operation; an approval does not claim that its source can never change later. There is no sender; a future sender must revalidate at claim time. No existing records are deleted or rewritten by cleanup.
